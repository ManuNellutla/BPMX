Feature specification

Extraction, documentation and BPMN visualization

The system converts PDF/PNG/DOCX/text, source code, video and BPMN inputs into a versioned JSON process model with evidence locators, then projects that model into documentation and BPMN 2.0 diagrams.

ModelCPM JSON, schema 1.0
NotationBPMN 2.0 XML
Evidence kindspage+bbox · file:line · timecode
Feature count12

01Capability map

Twelve features across three pillars. Extraction builds the model; documentation and visualization are projections of the same model.

02Feature catalogue

Priority: Core required for a usable v1; High completes the workflow; Later deferred.

Pillar 1 — Extraction

FEAT-01
EXTCore

Multimodal intake

Ingests PDF (text or scanned), PNG/JPG, DOCX/MD/TXT, source archives or repository URLs, MP4/MOV and BPMN XML. Selects text-layer or OCR, runs ASR and keyframe sampling, and records modality coverage.

in file / URL / archive
out source{sha256, modality, pages[], regions[], segments[], transcript[]}
→ REQ-EXT-01, 02, 03, 09, 10, 11
FEAT-02
EXTCore

Evidence & provenance

Binds every extracted element to a resolvable locator, a verbatim quote and a confidence value. Locator kinds: PDF page+bbox, image region, file:line range, video timecode range.

in source artifact + extraction candidate
out evidence{sourceId, locator, quote, confidence}
→ REQ-EXT-08, 14
FEAT-03
EXTCore

Process discovery

Extracts lanes, activities (verb–object), gateways with conditions, events, data objects, systems and handoffs. Normalises synonyms before graph assembly.

in evidence + text / transcript / static analysis
out lanes[] · nodes[] · edges[] · dataObjects[] · systems[]
→ REQ-EXT-03, 04, 05, 06, 07
FEAT-04
EXTCore

Value & outcome

Classifies value levers, captures KPI name/unit/baseline/target, generates an outcome statement, computes an impact estimate and a versioned priority score. Every inferred value is marked as an assumption.

in process model + source text
out value{levers[], outcome{}, kpis[], impact{}, automationPotential, priorityScore}
→ REQ-VAL-01 … 06
FEAT-05
EXTHigh

Cross-source fusion

Matches equivalent lanes, activities, gateways and events across sources. Merges duplicates with multi-source evidence and records disagreements as findings with dual citations.

in 2+ models or candidate sets
out merged model + findings[{type, elementId, citations[], resolution}]
→ REQ-EXT-12, 13

Pillar 2 — Documentation

FEAT-06
DOCCore

Canonical process model

Versioned JSON document validated against a published schema. Holds graph, value, evidence, findings and run provenance. All other outputs are generated from it.

in extracted model + human edits
out CPM JSON, immutable versions, current pointer
→ REQ-DOC-01, 02
FEAT-07
DOCCore

Process brief & registers

Generates a two-page brief: purpose, trigger, scope, outcome, actors, steps, exceptions, controls, systems, KPIs, risks. Assumptions and open questions are emitted as separate registers.

in CPM
out brief{sections[]} · assumptions[] · openQuestions[] · citations[]
→ REQ-DOC-03 … 08
FEAT-08
DOCHigh

Step table & RACI

One row per node with step number, activity, owner, RACI, system, input, output, control and element ID. Exported as CSV and embedded in the document pack.

in nodes[] + lanes[]
out rows[] · CSV · in-document table
→ REQ-DOC-04, 07
FEAT-09
DOCCore

BPMN 2.0 export & round-trip

Emits XSD-valid BPMN with deterministic DI layout, lanes, gateways, events and data objects. Evidence travels as namespaced extension elements; re-import preserves element IDs.

in CPM
out .bpmn XML · layout map · mapping report · change report on import
→ REQ-VIZ-01 … 04, REQ-MOD-06

Pillar 3 — Visualization

FEAT-10
VIZCore

Interactive BPMN canvas

Swimlane canvas with pan/zoom, minimap, fit, in-diagram search and collapsible lanes. Selecting a node opens the inspector and its citations; selecting a citation opens the source at the locator.

in CPM + evidence index
out rendered diagram · inspector state · citation navigation
→ REQ-VIZ-05, 06, 07, 10, 11
FEAT-11
VIZHigh

Portfolio & value views

Catalog filtered by domain, status, lever and confidence. Value heat overlay on steps, automation-potential scoring and a value-versus-effort matrix driven by the stored priority score.

in set of CPMs
out catalog[] · heat overlay · priority matrix · ranking
→ REQ-VIZ-08, REQ-VAL-05
FEAT-12
VIZHigh

Review, compare & export

Confidence-sorted review queue, inline corrections with human/AI provenance, version diff with change categories, semantic search, and export to PNG/SVG/PDF/CSV/JSON/BPMN.

in CPM versions + review state
out corrections[] · diff{added, removed, modified} · export artifacts
→ REQ-DOC-09, 10 · REQ-VIZ-09, 12 · REQ-MOD-05

03Pipeline

Stage boundaries correspond to persisted artefacts, so a run can be inspected and resumed at any stage.

04Value data model

Value is a typed block on the process model. Figures are derived from stored inputs; assumptions are fields, not footnotes.

FieldTypeRule
lever[]enum[] — cost, revenue, risk, compliance, customerExperience, cycleTimeExactly one primary; zero or more secondary. Free text rejected.
outcome.statementstringBaseline → target, KPI, horizon. Rendered from fields, not free-authored.
outcome.basisenum — cited | assumptionIf any clause is not evidenced, basis = assumption and the clause is listed in assumptions[].
kpis[]{name, unit, baseline, target, evidenceId?, assumed}Each value has a locator or assumed = true.
impact.annualisedUsdnumberRecomputable from method + assumptions[]; suppressed when a required input is missing.
impact.roundingenumSet by the least precise input; never more than two significant figures.
automationPotential0..1 + rationaleScore without rationale is invalid.
priorityScore{value, formulaVersion, inputs[]}Stored with contributory inputs; recomputation must match.
Priority formula — versioned
priority = w1·norm(impact)
         + w2·frequency
         + w3·automationPotential
         + w4·confidence
         − w5·riskExposure

weights  → policy/priority@1.0
inputs[] → stored per element
recompute → same inputs, same rank
Value block — JSON
{
  "lever": ["cycleTime", "cost"],
  "outcome": {
    "kpi": "DSO", "baseline": 48,
    "target": 38, "unit": "days",
    "basis": "assumption"
  },
  "impact": { "annualisedUsd": 230000,
              "confidence": 0.72 },
  "automationPotential": 0.62
}

05BPMN notation policy

Mapping contract between extracted content and BPMN elements. Content that cannot be mapped is demoted to an annotation and counted in the mapping report.

Source evidenceBPMN 2.0 elementRule
Role, department, external partyLaneOne lane per actor; each node has exactly one lane
Verb–object activity, handler, consumer, spoken stepTaskName normalised; synonyms merged
Human decision or manual approvalUser taskEvidence must indicate a person performs it
System-performed step from codeService taskCites the code construct
Decision diamond, if/else, status branchExclusive gatewayCondition verbatim; default flow allowed
Explicit concurrencyParallel gatewayNever inferred from list formatting
Trigger, message, schedule, terminal stateStart / intermediate / end eventEvent type only when evidenced
Named document or recordData objectAttached to producer or consumer
Named sub-flow or module boundarySubprocessCollapsed by default
Ambiguous, conflicting or unverifiable contentText annotation / candidateRequires human confirmation before promotion
Not modelled — v1
  • Choreography and conversation diagrams
  • Event sub-processes without explicit evidence
  • Message flows between pools
  • Executable attributes (expressions, form definitions)
  • Data stores (represented as systems + data objects)
Validation rules — pre-export
  • Exactly one start event per process; ≥1 end event
  • Gateway has ≥2 outgoing flows or a default
  • No unreachable node; no dangling edge
  • Every node assigned to a lane
  • Every flow node has ≥1 evidence locator
