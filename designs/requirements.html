System requirements and use cases

01Scope & design principles

This document specifies behaviour, not implementation. Model choice, inference hosting, deployment topology and security operations are treated as given and are not requirements here.

In scope

Extraction → Documentation → Visualization

  • Ingesting and normalising multimodal process evidence
  • Extracting actors, activities, gateways, events, data and systems
  • Extracting business value, outcomes and KPIs
  • Persisting a canonical, evidence-linked JSON model
  • Generating process documentation and BPMN 2.0 diagrams
  • Visualising, comparing and exporting the model
Out of scope

Execution and platform concerns

  • BPMN execution engines and task inboxes
  • RPA generation, code generation, live process mining
  • To-be simulation and optimisation
  • Model/provider selection and prompt engineering strategy
  • Hosting, tenancy, backups, disaster recovery
  • Authentication and authorisation mechanics

02The canonical model

All requirements refer to one artefact: the Canonical Process Model (CPM), a versioned JSON document. Evidence, value and provenance are not add-ons — they are fields on the model.

Essential shape — condensed example

// Abridged CPM document. Full sample: samples/cpm-invoice-to-cash.json
{
  "schemaVersion": "1.0.0",
  "id": "prc_01J8Q4Z9K2",  "version": 3,  "status": "approved",
  "name": "Invoice to Cash",  "domain": "Finance",
  "scope": { "trigger": "Invoice request received", "outcome": "Cash collected" },

  "lanes": [
    { "id": "lane_customer", "name": "Customer", "type": "external" },
    { "id": "lane_finance",  "name": "Finance",  "type": "internal" }
  ],

  "nodes": [{
    "id": "n_issue_invoice", "type": "serviceTask",
    "name": "Issue invoice", "laneId": "lane_finance",
    "confidence": 0.94,
    "evidence": [{
      "sourceId": "src_9f2a",
      "locator": { "kind": "page", "page": 4, "bbox": [412, 268, 548, 302] },
      "quote": "Finance issues the invoice within 24 hours",
      "confidence": 0.91
    }]
  }],

  "edges": [{ "id": "e_17", "from": "n_confirm_order", "to": "n_issue_invoice" }],

  "value": {
    "lever": ["cycleTime", "cost"],
    "outcome": { "statement": "Reduce DSO from 48 to 38 days",
                 "kpi": "DSO", "baseline": 48, "target": 38, "unit": "days" },
    "impact": { "annualisedUsd": 230000, "confidence": 0.72, "assumptions": ["AR base $40M", "WACC 12%"] }
  },

  "provenance": { "runId": "run_7c1e", "promptVersion": "extract@1.4.0",
                  "temperature": 0, "sourceHashes": ["sha256:6b1…", "sha256:af0…"] }
}

Schema authority. The CPM is the only artefact from which a brief, a step table or a BPMN file may be generated. Projections are regenerated; the model is never reconstructed from them.

03Extraction requirements

Fifteen requirements covering intake, interpretation and the evidence contract. REQ-EXT

IDRequirementAcceptance criteriaUse case
REQ-EXT-01 Multimodal intake. The system shall accept PDF, PNG, JPG, DOCX, Markdown, plain text, source-code archives and repositories, video (MP4/MOV) and BPMN 2.0 XML as process sources. Each accepted type produces a source record; an unsupported type is rejected with a list of supported formats; no job is created for a rejected source. UC-01
REQ-EXT-02 Source integrity. The system shall store a SHA-256 hash of every source and link every derived artefact to that hash. Hash is displayed in the source record; re-uploading identical bytes links to the existing source instead of creating a duplicate; deleting a derived artefact never alters the source. UC-01
REQ-EXT-03 Activity extraction. The system shall identify activities and normalise each to a verb–object name with an owning lane and, where stated, inputs, outputs and systems. Every activity has a name, lane and at least one evidence locator; synonyms of the same activity are merged; activity F1 ≥ 0.85 on the golden corpus. UC-01
REQ-EXT-04 Actor and lane extraction. The system shall identify roles, departments and external parties and assign every node to exactly one lane. No node is lane-less; actors with the same meaning are normalised to one lane; actor F1 ≥ 0.80 on the golden corpus. UC-01
REQ-EXT-05 Gateway extraction. The system shall identify decision points, classify them as exclusive, parallel or inclusive, and capture conditions verbatim where the source states them. Each outgoing flow has either a condition or is marked default; parallel gateways appear only where concurrency is explicit; gateway F1 ≥ 0.75. UC-01
REQ-EXT-06 Event extraction. The system shall identify start, intermediate and end events and type them (message, timer, error) only where the source evidences the type. Every process has at least one start and one end event; an untyped intermediate event is permitted; no event exists without a connecting flow. UC-01
REQ-EXT-07 Data and system extraction. The system shall extract named documents, records and systems of record, attaching each to the task that produces or consumes it. Unresolved references are listed as open questions rather than silently dropped; each system is linked to at least one task. UC-03
REQ-EXT-08 Evidence binding. The system shall bind every flow element to at least one locator (PDF page and bounding box, image region, file and line range, or video timecode), the verbatim quote, and a confidence value. Validation fails if any flow node lacks a locator; 100% of nodes in an approved model resolve to a source location; the quote is retrievable without re-parsing the source. UC-01
REQ-EXT-09 Diagram interpretation. The system shall interpret swimlanes, boxes, decision diamonds, arrows and labels in raster and vector diagrams, using OCR when no text layer exists. Swimlane boundaries and arrows are recovered on the golden diagram set; unreadable regions are reported with their bounding boxes; OCR confidence is propagated to elements. UC-02
REQ-EXT-10 Code interpretation. The system shall detect process-bearing constructs in source code — request handlers, queue consumers, schedulers, state machines, status enumerations, BPMN/DMN files and API descriptions — and map them to process elements. A detected construct cites file:line; a scheduled job is typed as a timer-triggered activity; an enumeration branch becomes a gateway condition. UC-03
REQ-EXT-11 Video interpretation. The system shall transcribe speech with timestamps and speaker labels, and read on-screen content from sampled keyframes. Each activity derived from speech carries a timecode accurate to ±5 seconds and a speaker label; on-screen text is captured where legible; illegible frames are flagged. UC-04
REQ-EXT-12 Cross-source fusion. The system shall merge equivalent elements across sources and record disagreements as findings, each retaining both citations. Duplicate activities from two sources collapse to one element with two evidence entries; an actor mismatch is reported as a conflict, not resolved silently. UC-05
REQ-EXT-13 Extraction modes. The system shall support full discovery, incremental extraction from newly added sources, and targeted questions about a specific process. An incremental run does not invalidate untouched elements; a targeted answer cites only in-scope evidence and declines questions outside the process boundary. UC-06
REQ-EXT-14 No unsupported assertions. The system shall place any element that cannot be evidenced into a candidate list with a reason, and shall never promote it to the model automatically. Unsupported-claim rate ≤ 3% on the golden corpus; every candidate states why evidence was insufficient; instruction-like text inside a source document cannot alter extraction behaviour. UC-07
REQ-EXT-15 Reproducibility. The system shall reproduce a model from the same sources, prompt version, parameters and seed, and store the run manifest with the model. Re-running with identical inputs yields an identical model excluding timestamps, job IDs and generation order; the manifest records source hashes, prompt version, parameters and seed. UC-16

04Business value requirements

Six requirements defining the typed value block. Figures are derived from stored inputs; assumptions are explicit fields. REQ-VAL

IDRequirementAcceptance criteriaUse case
REQ-VAL-01 Value lever classification. The system shall classify each process against a fixed set of levers: cost, revenue, risk, compliance, customer experience and cycle time. Exactly one primary lever and zero or more secondary levers are recorded; every approved process has a primary lever; classification is 100% within the fixed vocabulary. UC-14
REQ-VAL-02 Outcome statement. The system shall express each outcome as baseline → target, measured by a named KPI, within a stated horizon. All four fields are present or explicitly marked as an assumption; a missing baseline is never rendered as a number. UC-14
REQ-VAL-03 KPI capture. The system shall capture metric name, unit, baseline, target and the evidence that supports each value. Each KPI value resolves to a citation or is flagged as an assumption; units are consistent per KPI across the portfolio. UC-14
REQ-VAL-04 Impact estimate. The system shall produce an annualised impact estimate with its method and assumptions, and shall not report precision beyond its inputs. The estimate is recomputable from stored inputs; rounding follows the weakest input; a missing input suppresses the estimate rather than defaulting silently. UC-14
REQ-VAL-05 Automation potential and priority. The system shall score automation potential and compute a priority score from a versioned, explainable formula. Every score has a rationale and contributory inputs; the formula version is stored; recalculating with the same inputs produces the same ranking. UC-14
REQ-VAL-06 No silent value gap. The system shall require every approved process to carry an outcome or an explicit "no quantified outcome" marker with a reason. Approval is blocked when neither is present; the marker is visible in the catalogue and in exports. UC-14

05Documentation requirements

Ten requirements covering persistence, the narrative brief, tabular documentation and document-level traceability. REQ-DOC

IDRequirementAcceptance criteriaUse case
REQ-DOC-01 Canonical JSON model. The system shall persist every process as a JSON document validated against a published schema, with stable element identifiers. Schema validation passes before persistence; identifiers survive version changes and export/import; unknown fields are rejected with a path to the offending property. UC-08
REQ-DOC-02 Immutable versioning. The system shall create an immutable snapshot on every save and maintain a current-version pointer. Historical versions cannot be modified or deleted; restoring a version creates a new version rather than rewriting history. UC-08
REQ-DOC-03 Process brief. The system shall generate a brief containing purpose, trigger, scope, business outcome, actors, step summary, exceptions, controls, systems, KPIs, risks and open questions. All sections are present; the brief is at most two pages at default typography; an empty section states why it is empty. UC-09
REQ-DOC-04 Step table and RACI. The system shall produce a tabular view with one row per process node, including owner, RACI assignment, system, inputs, outputs and control. Row count equals node count; every row carries a stable element ID; CSV export preserves column order and quoting. UC-10
REQ-DOC-05 Assumptions and open questions. The system shall maintain registers of assumptions and open questions with owner and status. Every inferred value appears in the assumption register; unresolved evidence gaps appear as open questions; an empty register requires explicit confirmation. UC-09
REQ-DOC-06 Business outcome section. The system shall include outcome, KPI, impact estimate and confidence in every process document. The section is generated from the value block, not authored separately; a change in the model is reflected on regeneration. UC-09
REQ-DOC-07 Document export. The system shall export documentation to Markdown, HTML, PDF and DOCX with consistent structure and citations rendered as an appendix. All formats render the same section order; footnote numbering matches the appendix; no broken citations in any format. UC-09
REQ-DOC-08 Statement traceability. The system shall link every generated statement in a document to the model element or elements that support it. An orphan statement blocks publication; hovering a citation reveals the element ID and source locator. UC-09
REQ-DOC-09 Documentation diff. The system shall compare two versions and show added, removed and changed steps, owners, KPIs and evidence. Every change is categorised; unchanged content is visually de-emphasised; a diff can be exported. UC-13
REQ-DOC-10 Human edit provenance. The system shall mark human edits as human, retain the original extracted value, and record author, time and reason. No edit overwrites the original value; an approved version is read-only; reverting an edit restores the extracted value exactly. UC-07

06Visualization requirements

Twelve requirements covering BPMN validity, layout, the interactive canvas, evidence overlays and accessibility. REQ-VIZ

IDRequirementAcceptance criteriaUse case
REQ-VIZ-01 BPMN 2.0 validity. The system shall produce BPMN 2.0 XML that is schema-valid and semantically valid before any export. Zero schema errors and zero semantic errors (for example, a gateway with one outgoing flow) at export time; invalid models are blocked with element-level messages. UC-11
REQ-VIZ-02 Deterministic layout. The system shall lay out diagrams automatically with ordered lanes, a left-to-right flow and no overlapping nodes or edge labels. Repeated layout of the same model is identical; zero node overlaps across the layout corpus; lane order follows the model. UC-11
REQ-VIZ-03 Notation mapping. The system shall map model elements to BPMN per the published notation policy, demoting unmappable content to annotations rather than dropping it. No model element disappears between model and diagram; demoted content is visible as an annotation and counted in the mapping report. UC-11
REQ-VIZ-04 Round-trip. The system shall export BPMN that opens in at least two independent modelers, and shall re-import edited BPMN preserving identifiers and evidence extensions. No import errors in bpmn.io and Camunda Modeler; element IDs unchanged after round-trip; evidence extension elements survive the cycle. UC-11
REQ-VIZ-05 Interactive canvas. The system shall provide pan, zoom, fit-to-view, minimap, in-diagram search and collapsible lanes. All controls are operable by mouse and keyboard; the current viewport survives a selection change; collapse/expand preserves the model. UC-12
REQ-VIZ-06 Evidence overlay. The system shall indicate evidence per node and reveal the citation card with the source at the exact locator when the node is selected. Selecting a node shows its locator; selecting the citation opens the PDF at the page with the region highlighted, the video at the timecode, or the code at the line range. UC-12
REQ-VIZ-07 Node inspector. The system shall show activity details, owner, systems, inputs, outputs, confidence, evidence and value contribution for the selected node. Every displayed field comes from the model; low confidence is visually distinct; edits from the inspector follow REQ-DOC-10. UC-12
REQ-VIZ-08 Value visualization. The system shall overlay value, automation potential and risk on process steps and present a portfolio priority matrix. Overlay values match the model values exactly; the matrix uses the stored priority score; a legend explains every encoding. UC-14
REQ-VIZ-09 Version comparison. The system shall compare two versions side by side or as an overlay, highlighting inserted, removed and modified elements. Each change type has a distinct encoding and a legend; selecting a change reveals both versions and the underlying evidence. UC-13
REQ-VIZ-10 Accessibility. The system shall meet WCAG 2.2 AA for the diagram experience and expose every element through a text alternative. Every node is reachable by keyboard; a screen-reader list presents actors, activities and flows in order; contrast meets AA; no information is conveyed by colour alone. UC-12
REQ-VIZ-11 Diagram performance. The system shall render a 300-node, 15-lane model within two seconds and keep interaction responsive. First meaningful render ≤ 2 s at reference hardware; pan and zoom ≥ 50 fps at p95; progressive detail for dense models. UC-12
REQ-VIZ-12 Image and print export. The system shall export the diagram as PNG and SVG at 1× and 2× with a legend and without clipping. Exported bounds contain every element; text remains selectable in SVG; the legend is included and print layout respects page margins. UC-11

07Model & API contract

Six requirements that keep extraction, documentation and visualization connected by one contract. REQ-MOD

IDRequirementAcceptance criteriaUse case
REQ-MOD-01 API surface. The system shall expose REST resources for sources, extraction jobs, process models, versions, documentation, BPMN and exports, described by OpenAPI 3.1. Every UI capability is available through the API; the published specification matches the running service in contract tests. UC-01
REQ-MOD-02 Asynchronous jobs. The system shall return a job identifier immediately and report stage-level progress, including partial results on failure. A submission returns without waiting for extraction; progress events identify the current stage; a failed job preserves successfully extracted elements. UC-01
REQ-MOD-03 Schema contract. The system shall validate payloads against the published JSON Schema and reject incompatible changes without a major version. Schema and specification are validated in the build; a breaking change without a version increment fails the build. UC-08
REQ-MOD-04 Error contract. The system shall return errors in a consistent problem format with a machine-readable code, a human message and a correlation identifier. Every 4xx and 5xx response validates against the problem schema; the correlation identifier appears in logs. UC-01
REQ-MOD-05 Search. The system shall support semantic and keyword search across process models and evidence, returning cited snippets. Results include the process, the matched element and a citation; p95 response ≤ 500 ms at reference dataset size. UC-15
REQ-MOD-06 Import and export. The system shall export model JSON and BPMN with correct content types, and import BPMN with validation and a change report. Round-trip import produces a change report rather than a silent overwrite; malformed files return a validation error listing offending elements. UC-11

09Use cases

Sixteen use cases describe how the requirements are exercised end to end. Each links to the requirements it satisfies and the test cases that prove it.

UC-01

Extract a process from a PDF process pack

ExtractionP0
Primary actor
Process analyst
Goal
Obtain a structured, cited draft process model from a PDF containing narrative and a swimlane diagram.
Trigger
A discovery pack is received and needs to be turned into a model before a workshop.
Preconditions
A project exists; the PDF is readable and within size limits.
Postconditions
A draft CPM at version 1, an evidence index, and a confidence summary. Nothing is published.

Main flow

  1. The analyst uploads the PDF and selects the full-discovery mode.
  2. The system hashes the file, renders each page and detects a text layer.
  3. The system extracts narrative steps, then interprets the swimlane diagram (lanes, boxes, diamonds, arrows).
  4. Candidate elements are normalised and merged, and each is bound to a page and bounding box with a verbatim quote.
  5. The system identifies actors, activities, gateways, events, data objects and systems, and assembles the graph.
  6. The graph is validated against the model schema and the process is saved as a draft with a confidence summary.
  7. The analyst opens the process workspace and reviews the lowest-confidence elements first.

Alternate flow — no text layer

  1. At step 2 the system finds no text layer and switches to OCR.
  2. OCR confidence below threshold is propagated to affected elements, which are marked for review.
  3. The flow resumes at step 3; unreadable regions are reported with their bounding boxes.

UC-02

Extract a process from a scanned or photographed diagram

ExtractionP0
Primary actor
Process analyst
Goal
Recover a model from a whiteboard photo or a scanned handout where no machine-readable text exists.
Trigger
A workshop produces a photo of a whiteboard that no one has transcribed.
Preconditions
The image is legible at thumbnail scale; the project exists.
Postconditions
A draft model with lower confidence, explicit unreadable regions and a review task.

Main flow

  1. The analyst uploads the image and confirms the intended orientation.
  2. The system runs OCR and layout analysis, detecting shapes, lanes and connector lines.
  3. Text is associated with shapes; connectors are converted into sequence flows with direction.
  4. Low-confidence text is marked, and the element is linked to its pixel region.
  5. The draft is saved and the review queue is populated in confidence order.

Alternate flow — diagram not interpretable

  1. If shape detection yields no usable graph, the system reports the failure instead of fabricating a model.
  2. The analyst is offered the regions it could read and asked to supply a clearer source.

UC-03

Extract the implemented process from a code repository

ExtractionP1
Primary actor
Process analyst or engineer
Goal
Understand what the system actually does, with file-and-line evidence, independent of documentation.
Trigger
The documented process is suspected to differ from production behaviour.
Preconditions
A repository archive or URL is available and within size limits.
Postconditions
Service tasks, scheduled activities and branch conditions with code citations; no UI-derived elements invented.

Main flow

  1. The analyst supplies a repository archive or URL and optional include/exclude paths.
  2. The system inventories files and identifies process-bearing constructs.
  3. Handlers, consumers and schedulers become service tasks; state machines and status enumerations become gateways and conditions.
  4. Each element is bound to a file:line range and the relevant code excerpt.
  5. The model is saved as a draft labelled "implemented view", distinguishable from a documented view.

Alternate flow — monorepo above limits

  1. The system reports the size and suggests include/exclude scopes.
  2. Extraction runs on the selected scope and records the scope in the run manifest.

Extract a process from a recorded workshop

ExtractionP1
Primary actor
Process analyst
Goal

UC-05

Fuse sources and resolve conflicts

ExtractionP0
Primary actor
Process analyst
Goal
Produce one process model from a document, a recording and code, with disagreements made explicit.
Trigger
More than one source describes the same process.
Preconditions
At least two sources are ingested for the same process scope.
Postconditions
A merged model, a conflict register with dual citations, and recorded resolutions.

Main flow

  1. The analyst selects the sources to fuse and the process scope.
  2. The system matches equivalent lanes, activities, gateways and events across sources.
  3. Matched elements are merged, with each source retaining its own citation.
  4. Unmatched or contradictory elements are raised as findings with a category and both citations.
  5. The analyst accepts, rejects or annotates each finding; the decision is recorded against the element.

Alternate flow — irreconcilable scope

  1. If sources describe genuinely different processes, the system proposes separate models rather than forcing a merge.
  2. The analyst confirms the split; both models retain their original evidence.

UC-06

Ask a targeted question about a process

ExtractionP1
Primary actor
Process analyst or SME
Goal
Answer a narrow question — "what happens when payment fails?" — using only the evidence in scope.
Trigger
A review raises a specific question that the current model does not answer.
Preconditions
The process and its sources exist.
Postconditions
A cited answer plus candidate elements, or an explicit "not evidenced" response.

Main flow

  1. The analyst asks a question scoped to one process.
  2. The system retrieves only evidence within that process boundary.
  3. It answers with citations and proposes any new elements as candidates.
  4. The analyst accepts candidates into the model or discards them.

Alternate flow — out of scope or not evidenced

  1. If the question falls outside the boundary, the system declines and states the boundary.
  2. If evidence is insufficient, it says so and lists what would be needed.

UC-07

Review and correct a draft process

ReviewP0
Primary actor
Process analyst, then subject-matter expert
Goal
Correct errors efficiently by working from the lowest-confidence elements and their citations.
Trigger
A draft model is ready for review.
Preconditions
The draft has a confidence summary and an evidence index.
Postconditions
A corrected draft with human provenance recorded for every change.

Main flow

  1. The system presents elements ordered by confidence, lowest first, and a review queue.
  2. The analyst opens an element, sees its citation and either accepts or edits it.
  3. Edits record author, time, reason and the original extracted value.
  4. Unsupported content is shown as a candidate and is not promoted without confirmation.
  5. The review status is saved; accepted elements are removed from the queue.

Alternate flow — evidence is wrong

  1. The analyst rejects the citation, which flags the source region as unreliable.
  2. The element returns to candidate status rather than remaining in the model.

UC-08

Approve and publish a process version

GovernanceP0
Primary actor
Process owner
Goal
Turn a reviewed draft into an immutable, approved version that documentation and diagrams can reference.
Trigger
Review is complete and findings are resolved or accepted.
Preconditions
Model schema-valid; no blocking open questions; value section present or explicitly marked.
Postconditions
An immutable approved version and a current-version pointer; previous versions remain readable.

Main flow

  1. The owner reviews the readiness checklist: schema, evidence, value, conflicts.
  2. The system blocks approval if a required check fails and names the offending elements.
  3. The owner approves and supplies a rationale.
  4. The system writes an immutable snapshot and moves the current pointer.
  5. The approved version becomes the basis for documents, BPMN export and comparison.

Alternate flow — approval after changes

  1. If the model changes after approval, a new draft is created.
  2. The approved version remains untouched; the draft is diffed against it.

UC-09

Generate the process brief and registers

DocumentationP0
Primary actor
Process owner or analyst
Goal
Produce a one-page brief plus assumptions and open-questions registers that stakeholders can circulate.
Trigger
A model is approved, or a draft is needed for a steering meeting.
Preconditions
The model exists and its value block is populated.
Postconditions
A document pack with citations, exportable in four formats.

Main flow

  1. The user requests a brief and selects a version.
  2. The system assembles sections from the model, never re-summarising the sources.
  3. Each statement is linked to its element IDs and citations.
  4. Assumptions and open questions are rendered from the registers.
  5. The user previews, then exports to Markdown, HTML, PDF or DOCX.

Alternate flow — missing KPI

  1. Where no quantified outcome exists, the brief states "no quantified outcome" and links the reason.
  2. The section is never filled with an invented figure.

UC-11

Export BPMN and open it in an external modeler

VisualizationP0
Primary actor
Enterprise architect
Goal
Hand the process to an existing modelling practice without losing structure or evidence links.
Trigger
The client standardises on Camunda Modeler or a similar tool.
Preconditions
The model is schema-valid and passes semantic checks.
Postconditions
A BPMN 2.0 file that opens cleanly, plus a mapping report for demoted content.

Main flow

  1. The user requests BPMN export for a version.
  2. The system validates the model and runs deterministic auto-layout.
  3. Evidence links are written as namespaced extension elements.
  4. The system generates BPMN 2.0 XML and validates it against the schema and semantic rules.
  5. The user downloads the file and opens it in an external modeler.
  6. After local edits, the user re-imports; identifiers and evidence links are preserved.

Alternate flow — validation failure

  1. The export is blocked and each error names the offending element.
  2. The user is taken to the element in the canvas to fix it.

Assess and prioritise business value

ValueP1
Primary actor
Portfolio lead or transformation sponsor
Goal
Decide where to act first, using comparable outcomes rather than volume of process maps.
Trigger
Several processes have been discovered and capacity is limited.
Preconditions
At least two processes have a value assessment.
Postconditions
A ranked shortlist with visible assumptions and confidence.

Main flow

  1. The portfolio lead opens the value dashboard.
  2. The system classifies each process by lever and shows KPI, impact and confidence.
  3. The priority score is computed from the stored, versioned formula.
  4. The lead inspects the matrix and drills into any process.
  5. The lead exports the shortlist with assumptions attached.

Alternate flow — insufficient inputs

  1. Where an impact cannot be computed, the process is shown as "not quantified" and excluded from ranking.
  2. The reason is visible, so the gap can be closed rather than guessed.

10Glossary

TermDefinition
CPMCanonical Process Model — the versioned JSON document that is the system of record for a process.
LocatorA precise, resolvable pointer to evidence: page and bounding box, image region, file and line range, or video timecode range.
Evidence coveragePercentage of model elements that carry at least one resolvable locator.
Unsupported claimAn element or statement in a model or document that cannot be resolved to a source locator.
CandidateAn extracted element with insufficient evidence. Visible for review, never promoted automatically.
Golden corpusA fixed, human-adjudicated set of sources and expected models used to measure extraction quality and guard against regression.
FusionMerging equivalent elements from multiple sources while retaining each citation and surfacing conflicts.
Value leverThe mechanism by which a process improvement creates value: cost, revenue, risk, compliance, customer experience or cycle time.
Round-tripExport to BPMN, edit in an external modeler, re-import — preserving identifiers and evidence.
DriftA difference between versions of a process caused by a new source, a code change or a human correction.
Notation policyThe published mapping from extracted content to BPMN elements, including what is deliberately demoted to annotations.
